# 부록 7 - ML/AI 워크로드에서 Hubble을 활용한 성능 분석 전략

### 1. 먼저, ML/AI 워크로드에서 봐야 할 것들

ML/AI에서 네트워크 성능이 이슈가 되는 곳

- **모델 다운로드/업로드**: HuggingFace, S3, GCS 등과의 대용량 전송
- **노드 간 통신**: parameter server, feature store, shard 간 데이터 셔플
- **GPU 노드 ↔ 스토리지/서비스**: 학습/추론 시 지속적인 I/O
- **외부 API 호출**: OpenAI, Bedrock, Vertex AI 같은 L7 호출

Hubble로 이 네 가지를 **흐름(flow)** 단위로 잡아내는 게 핵심.

### 2. 기본 관점: “어디가 막히고, 어디가 느린지”를 흐름으로 본다

Hubble에서 성능 분석은 크게 두 축으로 이루어짐

- **DROPPED / REJECTED**: 정책·라우팅·암호화 때문에 막힌 트래픽
- **SLOW / RETRIES**: 지연(latency)·재전송·L7 에러가 많은 트래픽

이걸 ML/AI 워크로드에 맞게 필터링해서 추적해야 함

### 3. 패턴 1 — 모델 다운로드/업로드 병목 찾기

대형 모델 파일이 느리게 받아질 때, Hubble 사용법

- **특정 Pod ↔ 외부 도메인(HuggingFace/S3 등) 흐름만 필터링**
    - `namespace=ml`, `app=model-downloader` 같은 라벨 기준
- 흐름에서 보는 것:
    - **지연(latency)**: RTT가 비정상적으로 높은지
    - **재전송**: TCP 재전송이 많은지
    - **DROPPED**: 중간에 정책이나 Egress Gateway에서 막히는지

이걸 보면 병목이

- 클러스터 내부인지,
- Egress Gateway인지,
- 외부 네트워크(WAN)인지
파악하는 것이 가능

### 4. 패턴 2 — 노드 간 통신(학습/분산 처리) 병목 찾기

분산 학습이나 데이터 셔플링이 느릴 때는 **노드 간 흐름**을 보는 게 중요.

- **trainer ↔ parameter-server**, **worker ↔ shard** 같은 라벨 기준으로 필터
- 보는 포인트:
    - **노드 간 지연**: 특정 노드 쪽으로 갈 때만 느린지
    - **DROPPED**: 정책·암호화(IPsec/WireGuard)·MTU 문제로 Drop되는지
    - **불균형 흐름**: 일부 노드에만 트래픽이 몰려 있는지

이걸로

- 특정 노드의 NIC/CPU가 병목인지,
- Cilium 정책이 과하게 막고 있는지,
- 암호화가 특정 경로에서만 부담이 되는지
를 찾을 수 있슴

### 5. 패턴 3 — GPU 노드 성능 분석

GPU 노드는 네트워크 병목이 곧 **학습/추론 속도 저하**로 이어지니까, Hubble로 따로 보는 게 좋음.

- **node-type=gpu** 같은 라벨로 GPU 노드에 올라간 Pod만 필터
- 보는 것:
    - **GPU 노드 ↔ 스토리지/DB 흐름**: I/O 지연이 있는지
    - **GPU 노드 ↔ 외부 서비스 흐름**: Egress가 느린지
    - **DROPPED**: GPU 노드로 들어오는/나가는 트래픽이 정책 때문에 막히는지

여기서 병목이 보이면:

- Egress Gateway로 외부 트래픽을 우회시키거나
- GPU 노드에 붙은 Cilium/Envoy 리소스를 조정하는 식으로 튜닝 포인트가 생김

### 6. 패턴 4 — 외부 API 호출(OpenAI 등) 성능 분석

실시간 추론, 추천, LLM 호출 같은 건 **L7 성능**이 곧 서비스 품질이라서, Hubble의 L7 관측이 중요.

- **특정 서비스 ↔ 외부 FQDN 흐름** 필터
    - 예: `api.openai.com`, `huggingface.co`
- 보는 것:
    - **HTTP method/path**: 어떤 엔드포인트가 느린지
    - **에러율**: 4xx/5xx 비율
    - **지연 분포**: 평균/최대 latency
    - **재시도 패턴**: 같은 요청이 여러 번 전송되는지

이걸로

- 외부 API 자체가 느린 건지,
- 우리 쪽 네트워크/Egress가 문제인지,
- 클라이언트 코드가 과도하게 재시도하는지
구분할 수 있슴

### 7. 패턴 5 — 정책/암호화가 성능을 깎고 있는지 확인

ML/AI 워크로드는 정책·암호화·Egress가 다 켜져 있는 경우가 많음 → 성능이 “보안 설정 때문에” 떨어지는 경우가 많음.

Hubble로 볼 수 있는 것:

- **DROPPED 흐름 + 정책 정보**
    - 어떤 CiliumNetworkPolicy가 막았는지
    - 의도치 않게 막고 있는 경로가 있는지
- **암호화 흐름**
    - 특정 노드/경로에서 암호화된 트래픽이 과도하게 많은지
    - 암호화가 켜진 후 지연이 급증한 구간이 있는지

이걸 기반으로:

- 정책을 더 “성능 친화적으로” 재설계하거나
- 암호화 경로를 조정하는 식으로 튜닝 포인트를 찾을 수 있슴.

### 8. 실제로 쓸 때의 사고 흐름

ML/AI 성능 문제를 Hubble로 볼 때, 대략 이런 순서로 생각:

1. **문제가 되는 워크로드를 라벨/네임스페이스로 좁힌다**
    - `namespace=ml`, `app=trainer`, `app=inference` 등
2. **그 워크로드의 흐름만 본다**
    - 내부 ↔ 내부, 내부 ↔ 외부 둘 다
3. **DROPPED / 높은 latency / 높은 에러율 흐름을 중심으로 본다**
4. **병목 위치를 구분한다**
    - Pod 내부?
    - 노드 간?
    - Egress Gateway?
    - 외부 서비스?
5. **정책·암호화·Egress 설정과 연결해서 튜닝 포인트를 찾는다**

ML/AI 환경이 아래 중 어디에 해당하는지에 따라 어디를 먼저 볼지 결정해야 함

- 분산 학습 위주인지,
- 실시간 추론/추천 위주인지,
- 외부 LLM API를 많이 쓰는지
